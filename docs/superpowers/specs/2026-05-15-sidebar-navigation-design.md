# QADB 侧边导航分层设计

## 背景

当前左侧侧边栏直接平铺 9 个一级入口：

- 首页
- 常用
- 终端
- 按键事件
- 应用
- 文件浏览
- 日志
- 进程
- 设置

入口数量过多，导致主任务识别成本偏高。`终端 / 按键事件 / 文件浏览 / 日志 / 进程` 都属于工具型、调试型页面，频率与“首页 / 常用 / 应用 / 设置”相比更低，适合下沉为二级导航。

## 目标

- 将侧边栏一级导航收敛为 5 项，突出高频主任务
- 保持现有页面 route 不变，避免扩大改动范围
- 保持顶部菜单中的页面跳转能力继续可用
- 在进入任一二级页时，让用户明确感知自己仍处于“工具”分组内

## 非目标

- 不重构 `NavHost` 路由结构
- 不新增独立的“工具首页”页面
- 不调整各页面内部布局与功能
- 不改动顶部菜单的信息架构

## 信息架构

一级导航调整为：

- 首页
- 常用
- 应用
- 工具
- 设置

“工具”分组下的二级导航为：

- 终端
- 按键事件
- 文件浏览
- 日志
- 进程

## 交互设计

### 一级导航行为

- 点击 `首页 / 常用 / 应用 / 设置` 时，直接进入对应页面
- 点击 `工具` 时，不作为独立页面跳转
- 点击 `工具` 仅负责展开或收起二级导航

### 二级导航行为

- 点击二级项时，进入其对应的现有 route
- 当前 route 属于工具组时，`工具` 分组自动保持展开
- 当前 route 对应的二级项高亮显示

### 展开状态规则

- 默认情况下，如果当前页面不在工具组，`工具` 初始为收起
- 如果当前页面在工具组，`工具` 初始为展开
- 用户手动展开后，在切换到工具组内页面期间保持展开
- 用户切换到非工具组页面后，可恢复为收起状态

### 视觉规则

- 一级项继续沿用当前侧边栏视觉风格
- `工具` 作为分组项，增加展开/收起指示
- 二级项在视觉上相对一级项缩进，并减弱层级重量
- 当二级项被选中时，保持与当前选中态一致的品牌色反馈，但弱于一级页面主选中态

## 实现边界

### 路由

- 保留现有 route：
  - `home`
  - `common`
  - `app`
  - `terminal`
  - `keyevent`
  - `filebrowser`
  - `log`
  - `process`
  - `setting`
- `AppMenuCommand.Navigate(route)` 继续直接导航到具体 route
- 顶部菜单里的“页面导航”无需修改映射关系

### 代码结构

预期仅做小范围实现调整：

- `App.kt`
  - 将侧边栏数据源从简单平铺列表改为“一级项 + 工具分组”的结构
  - 保留现有 `navigateToRoute()` 和 `NavHost`
- `widget/Sidebar.kt`
  - 新增分组项与二级项渲染能力
  - 根据 `selectedRoute` 判断工具组是否展开、哪个二级项处于选中
- `strings.xml` / `strings-en.xml`
  - 仅在缺少分组文案时补充必要字符串

## 风险与约束

- 当前工作区存在未提交改动，实现时必须避免覆盖用户现有修改
- 侧边栏目前没有通用的可展开分组组件，因此实现应限定在 `Sidebar.kt` 内，避免扩散到全局 UI 组件层
- 由于 `工具` 不是 route，必须明确区分“分组展开”与“页面导航”两类点击行为

## 验收标准

- 左侧一级导航减少为 5 项
- `终端 / 按键事件 / 文件浏览 / 日志 / 进程` 不再作为一级项直接平铺
- 点击 `工具` 可以展开并看到上述 5 个二级入口
- 进入任一工具页时，对应二级项高亮，且工具组保持展开
- 顶部菜单的页面跳转仍能正确打开所有页面
- 现有页面 route 和页面内容不发生行为回归

## 验证计划

- 先运行最快的 Kotlin 编译检查，确认类型与 Compose API 无误
- 手动验证以下路径：
  - 一级项切换：首页、常用、应用、设置
  - 工具组展开/收起
  - 二级项跳转：终端、按键事件、文件浏览、日志、进程
  - 顶部菜单跳转到工具页后，侧边栏状态是否正确同步

## 实现建议

采用“侧边栏分组展开，保留单层 route”的实现方式。这一方案不改变现有页面注册和菜单跳转逻辑，只调整导航展示层，能把 diff 控制在最小范围内，同时满足一级收敛和二级导航的需求。
